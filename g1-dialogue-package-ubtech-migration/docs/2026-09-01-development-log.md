# 宇树 G1 智慧语音对话系统开发日志

日期：2026年9月1日  
项目：宇树 G1 智慧语音对话  
状态：完整链路已跑通，首轮性能优化已完成

## 1. 今日目标

今天的工作目标是从机器人开机后无法回答的问题开始，恢复并完善一套可运行、可测量、可优化的智慧语音对话系统。最终需要实现：

1. 机器人能够通过内置麦克风识别用户说话。
2. 识别文本经过本地知识库检索和千问模型生成回答。
3. 中文回答能够通过机器人扬声器正常播放。
4. 支持唤醒词和连续多轮对话。
5. 自动记录 ASR、模型、TTS、首响、整轮耗时和异常率。
6. 使用同一组测试问题完成优化前后 A/B 对比，用数据验证效果。

## 2. 最终系统架构

```text
用户说话
   ↓
G1 麦克风与固件 ASR
   ↓  rt/audio_msg
g1_voice.cpp 提取 ASR 最终文本
   ↓  /tmp/hear5.log
g1_bridge.py 唤醒词与连续会话状态机
   ↓
knowledge_base.py 检索本地知识库
   ↓
qwen_client.py 调用千问大模型
   ↓
Edge TTS 合成中文 MP3
   ↓
GStreamer 转换为 16 kHz、单声道、16 bit PCM WAV
   ↓
g1_play_wav.cpp 调用 Unitree PlayStream
   ↓
G1 扬声器播放回答
   ↓
CSV/JSONL 记录逐轮性能和异常信息
```

## 3. 网络结构

控制电脑使用双网卡，机器人通信和互联网访问相互独立：

| 网络接口 | 地址 | 用途 |
|---|---|---|
| `enp11s0f1` | `192.168.123.18/24` | 只负责连接宇树机器人内网 |
| `wlp0s20f3` | `192.168.77.115/24` | 负责调用千问和 Edge TTS 等外网服务 |

设计原则：机器人有线网卡不配置默认路由，系统默认路由走 WiFi，避免机器人内网和互联网路由冲突。

## 4. 今日完成内容

### 4.1 恢复机器人语音对话

机器人重新开机后出现“用户说话但机器人不回答”的现象。检查并重新启动以下组件：

- `g1_voice`：订阅机器人 `rt/audio_msg`，输出 ASR 文本。
- `g1_bridge.py`：处理唤醒、知识库、大模型、TTS和播放。
- `g1_play_wav`：把PCM音频通过 Unitree SDK发送给机器人。

恢复后机器人能够正常响应唤醒词并回答问题。

### 4.2 清理重复和残留进程

发现旧版桥接程序可能残留，存在新旧版本同时运行的风险。处理内容：

- 清理重复的 `g1_voice` 进程。
- 清理旧版 `g1_bridge.py` 和新版性能版桥接进程。
- 修改启动脚本中的进程匹配表达式，避免误杀启动脚本自身。
- 确保系统中同时只运行一套 ASR 和一套对话桥接服务。

### 4.3 解决中文 TTS 无声问题

当前固件的内置中文 TTS 接口返回成功，但机器人没有可听声音。因此改为外部合成和PCM播放：

1. 使用 Edge TTS 的 `zh-CN-XiaoxiaoNeural` 合成 MP3。
2. 使用 GStreamer 转换为 `S16LE / 16000 Hz / 单声道` WAV。
3. 使用 `g1_play_wav.cpp` 读取 PCM 数据。
4. 每次发送 32000 字节音频，通过 `AudioClient.PlayStream` 播放。
5. 播放结束后调用 `PlayStop` 关闭当前音频流。

### 4.4 建立唤醒与连续对话状态机

系统包含以下状态：

| 状态 | 行为 |
|---|---|
| `idle` | 只接受“你好”“小宇”等唤醒词，忽略普通环境语音 |
| `listening` | 唤醒后进入连续对话，可直接追问 |
| `paused` | 用户说“停止”“闭嘴”等指令后暂停回答 |

同时实现：

- 过滤过短、无意义的识别结果。
- 清理唤醒词后再发送真实问题。
- 保存最近3轮对话历史，支持上下文追问。
- 对回答中的链接、Markdown符号和表情进行清理。
- 回答过长时按中文标点截断，避免机器人长时间播报。

### 4.5 接入本地知识库

知识库位于 `knowledge/`，当前共加载133条问答数据。实现方式：

- 使用 `BAAI/bge-small-zh-v1.5` 生成中文语义向量。
- 对知识库问题和答案建立归一化向量。
- 用户提问时计算余弦相似度。
- 取最相关的2条知识作为大模型上下文。
- 知识库没有答案时允许模型使用通用知识回答。

### 4.6 建立性能监控和异常记录

每轮对话自动记录以下字段：

- 轮次ID、时间戳、会话状态、问题文本。
- ASR最终文本接收时间。
- 人工 ASR结束标记到最终文本的耗时（取得有效标记时）。
- 知识库检索耗时。
- 模型响应耗时。
- TTS合成耗时。
- 音频转换耗时。
- 播放调用到首个音频包的耗时。
- ASR最终文本到音频首包的系统首响。
- 整轮播放完成时间。
- 回答字数、成功状态、异常阶段和异常类型。

输出文件：

```text
logs/performance_metrics.csv
logs/performance_metrics.jsonl
logs/performance_summary.md
```

## 5. 遇到的问题和解决办法

### 问题1：机器人开机后不回答

原因判断：语音监听或桥接进程未恢复，并可能存在旧进程干扰。

解决办法：

- 检查双网卡地址和路由。
- 检查机器人内网设备是否在线。
- 清理残留进程。
- 分别启动 ASR监听、桥接和播放程序。
- 查看 `/tmp/hear5.log` 与 `/tmp/bridge.log` 定位异常阶段。

结果：机器人恢复唤醒和连续对话。

### 问题2：中文内置 TTS 没有声音

原因判断：当前固件的内置中文 TTS 与现场版本不兼容。

解决办法：使用 Edge TTS 生成音频，再转换成机器人播放接口要求的 PCM WAV。

结果：中文回答可以通过机器人扬声器正常播放。

### 问题3：模型回答和首响偏慢

优化前数据显示，模型响应和TTS合成占首响的大部分：

- 模型响应平均约1.15秒。
- TTS合成平均约2.01秒。
- 知识库检索和音频转换只有几十毫秒，不是主要瓶颈。

解决办法：优先优化模型、回答长度和TTS，不在低占比环节浪费开发时间。

### 问题4：ASR耗时不能自动准确统计

原因判断：当前 G1 ASR只输出最终文本，没有提供“用户说完最后一个字”的事件或音频帧时间戳。人工回车标记在本轮测试中没有成功记录。

解决办法：

- 本次报告不填写或编造ASR耗时。
- 系统首响统一从收到ASR最终文本开始计算。
- 后续接入 VAD 或声音能量检测，自动获取语音结束时间。

真正的口到耳首响应计算方式：

```text
口到耳首响 = ASR耗时 + ASR最终文本到音频首包耗时
```

### 问题5：连续会话可能误响应环境人声

原因判断：测试结束后仍处于 `listening` 状态，环境中的电视或人员说话可能被识别为后续问题。

解决办法：

- 测试结束后重启桥接服务，将状态恢复为 `idle`。
- `idle` 状态下只处理包含唤醒词的语音。
- 后续增加固定会话上限、ASR置信度和误唤醒统计。

## 6. 性能优化过程

### 6.1 保存优化前基线

固定同一组10个问题，连续执行完整链路，不使用回答缓存。保存优化前代码、逐轮CSV和汇总报告，确保优化结果可追溯。

### 6.2 模型小样本选型

使用相同问题分别测试 `qwen-plus` 和 `qwen-turbo`：

| 模型 | 单次响应范围 |
|---|---:|
| `qwen-plus` | 约820至1300 ms |
| `qwen-turbo` | 约408至410 ms |

确认 `qwen-turbo` 的回答质量满足现场语音问答后进行切换。

### 6.3 实施优化

本轮代码调整：

1. 模型由 `qwen-plus` 调整为 `qwen-turbo`。
2. 回答约束由最多80字调整为一句话、40字以内。
3. 最大输出由120 Token降为80 Token。
4. 最近对话历史由5轮减少为3轮。
5. 知识库候选由3条减少为2条。
6. TTS语速由 `+5%` 调整为 `+15%`。

### 6.4 使用原问题复测

优化后继续使用原来的10个问题、相同顺序和相同播放链路复测，避免测试集变化造成数据失真。

## 8. 数据结论

- 模型响应平均缩短627 ms，提升54.5%。
- 系统首响平均缩短834 ms，提升23.7%。
- 系统首响P95从4464 ms降到3160 ms，长尾等待明显改善。
- 整轮播放平均缩短5839 ms，提升39.9%。
- 优化后10轮全部成功，异常率保持0%。
- 回答长度明显下降，更适合现场语音交互。

本轮优化在没有降低稳定性的情况下，明显改善了机器人开始回答的速度和整轮交互时间。

## 10. 当前状态和限制

当前已实现：

- G1内置ASR文本接收。
- 唤醒词与连续多轮对话。
- 本地知识库RAG。
- 千问模型回答。
- 中文TTS与机器人扬声器播放。
- 自动性能埋点、汇总和异常分类。
- 可配置网卡、SDK路径、日志路径和模型。

当前限制：

- 千问和 Edge TTS依赖互联网，不属于完全内网部署。
- 缺少自动语音结束事件，暂时无法精确统计ASR耗时。
- TTS仍需完成整段合成后才开始播放，首响还有优化空间。
- 连续会话需要进一步增加误唤醒保护。
