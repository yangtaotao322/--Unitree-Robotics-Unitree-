## 四、实际遇到的问题

1. 优必选默认地址`192.168.11.3`当前Ping不通，SSH 22端口也不可达，因此无法执行实体机鉴权和播报。

3. 开发电脑本机未安装`udoke`和`ros2`。根据厂商文档，这些工具应在优必选设备及其`demo_runtime`容器中使用，不能在当前电脑上假装完成SDK测试。
4. SDK的`play_text`同步返回只表示请求已受理，直接把返回成功当成播报成功会产生假阳性。
5. SDK事件不是历史回放语义，播报后再订阅可能丢失事件，因此代码必须先订阅再调用。
6. ROS2服务依赖容器中的`rclpy`、`robo_sdk`和`std_srvs`，普通电脑不能直接执行真实适配器。
7. SDK文档没有直接给出ASR文字接口，后续语音输入需要读取音频共享内存并接入独立ASR。

### 7.2 解决的问题

#### 1. 机器狗在Gazebo中不移动

实际原因是运动控制器虽然已经启动，但没有进入接收`/cmd_vel`的Navigation模式。

处理步骤：

1. 让机器狗起身。
2. 切换至行走控制状态。
3. 开启Navigation模式。
4. 确认`/cmd_vel`同时存在发布者和订阅者。

处理后，机器人能够正常响应巡检节点发布的速度指令。

#### 2. 仿真处于楼梯场景

楼梯场景会放大基础路径控制的难度，转向、速度变化和台阶接触叠加后容易造成翻倒，无法单独判断巡检控制本身是否正确。

处理步骤：

1. 将Gazebo场景切换为平坦的`earth.world`。
2. 优先在平地验证路径控制、到点精度和任务状态机。
3. 将楼梯、斜坡和复杂地形保留为后续专项测试。

#### 3. 缺少可靠的位置反馈

仅依靠速度指令积分推算位置会产生累计误差，不能可靠判断是否到达A、B、C巡检点。

处理步骤：

1. 为Gazebo模型增加Ground Truth里程计插件。
2. 发布`/ground_truth/odom`。
3. 使用Gazebo中的真实位姿进行闭环控制。
4. 实时计算机器人与目标点之间的距离和航向误差。

改造后可以准确记录每个巡检点的实际到点误差。

#### 4. 机器人出现翻车、摔倒

早期测试中，较大的转向指令、线速度和楼梯场景叠加，导致机器人翻倒。

处理步骤：

1. 重置仿真和机器人姿态。
2. 限制最大线速度和最大角速度。
3. 航向误差过大时停止直行，优先完成转向。
4. 转向过程中自动降低线速度。
5. 切换到平坦场景重新验证。
6. 增加roll、pitch翻倒检测。
7. 倾斜超过约`0.8 rad`时立即发送零速度并终止任务。

优化后，多轮快速巡检中未再次出现摔倒。

#### 5. 到点误差无法继续减小

收紧到点要求后，机器人在距离目标约0.147米处不再前进。实际原因是底层强化学习行走控制器存在低速指令死区，速度指令过小时不会产生明显位移。

处理步骤：

1. 增加最低有效线速度。
2. 接近目标时仍保持足以驱动机器人的速度。
3. 将到点容差设置为约0.15米。
4. 在到点精度和目标附近抖动之间进行平衡。

最终到点误差稳定在约0.145～0.150米。继续机械收紧阈值不会带来真实精度提升，反而会增加抖动和超时。

#### 6. C点发生超时重试

一次测试中机器人已经接近C点，但恰好在超时边界附近才进入到点范围，触发了重试。

处理步骤：

1. 调整最低有效速度，改善末端收敛。
2. 调整单个巡检点的超时时间。
3. 在稳定范围内提高巡航速度。
4. 保留有限次数重试，防止任务无限等待。

后续两轮快速巡检中，C点均一次到达，没有再次触发重试。

#### 7. 初次生成的ZIP无法解压

第一次生成的文件虽然使用`.zip`后缀，但内部格式不是Windows标准ZIP。

处理步骤：

1. 使用Windows标准压缩方式重新生成。
2. 在本机实际执行解压验证。
3. 检查压缩包中的全部文件。
4. 排除`.git`、`__pycache__`、日志和构建产物。
